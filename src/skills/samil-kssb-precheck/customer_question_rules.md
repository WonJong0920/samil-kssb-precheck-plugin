# 고객 확인 질문 생성 규칙 (Customer Question Rules)

사전검토의 핵심 가치는 "확인 불가/부족 근거"를 **컨설턴트가 고객에게 물어볼 수 있는 질문**으로 전환하는 것이다.
이 문서는 질문 생성 규칙과 필드 구조를 정의한다.

## 1. 언제 질문을 생성하는가

- 판정이 **"확인 불가"**인 항목: 반드시 질문을 생성한다.
- 판정이 **"일부 근거 확인, 보완 필요"**인 항목: 부족한 부분(예: 수치·산정범위)을 채우기 위한 질문을 생성한다.
- 판정이 **"상충 또는 해석 필요"**인 항목: 기준·범위·기준연도를 확인하는 질문을 생성한다.
- **"근거 확인"** 항목은 원칙적으로 질문을 생성하지 않는다(필요 시 근거 강화용 선택 질문만).

> 질문은 항상 **부족하거나 확인 불가한 근거에서** 나온다. 근거가 충분한 곳에서 임의로 질문을 만들지 않는다.

## 2. 질문 필드 구조

각 질문은 다음 필드를 갖춘다(참고 엔진의 customer_questions 구조 계승):

| 필드 | 설명 |
|---|---|
| 항목ID | 대응하는 KSSB 카탈로그 항목 ID |
| 항목명 | 공시요구 항목명 |
| 질문 | 고객에게 물을 실제 질문 문장 |
| 질문사유 | 왜 묻는가(어떤 근거가 없거나 부족한가) |
| 관련근거 | 연결된 근거 앵커(있으면). 없으면 "해당 없음" |
| 우선순위 | 상 / 중 / 하 |
| 요청자료 | 고객에게 요청할 구체 자료(예: 이사회 규정, 산정 명세, 데이터표) |
| 후속조치 | 자료 수령 후 컨설턴트가 할 일(예: 원문 대조 후 상충 해소 확인) |

> **findings 스키마 필드 매핑**: 항목ID·항목명은 상위 finding_item(`item_id`·`requirement_title`)에서 파생하며,
> 질문 객체(`customer_question`)의 필드는 질문=`question`, 질문사유=`reason`, 관련근거=`related_evidence`(없으면 "해당 없음"),
> 우선순위=`priority`(high/medium/low), 요청자료=`requested_material`, 후속조치=`follow_up_action`이다.
> 이 6개 필드는 스키마에서 **모두 필수**다(`schemas/findings_schema_contract.md`).

## 3. 우선순위 기준(권장)

- **상**: 정량 핵심 지표 누락(온실가스 배출량, 에너지 사용량), 상충 근거, 거버넌스 감독 책임 미확인.
- **중**: 정성 서술 보완 필요, 재무영향 정성/정량 보강.
- **하**: 조건부 항목 적용 여부 확인 등.

## 4. 질문 작성 원칙

- 질문은 **자료로 답할 수 있는 형태**로 쓴다("~를 확인할 수 있는 자료가 있습니까?").
- 하나의 질문에 하나의 부족분을 담는다(복합 질문 지양).
- 고객을 압박·평가하는 표현을 피하고, 보완을 돕는 톤을 유지한다.
- 확정·판정 표현("미준수", "부적합")을 질문에 넣지 않는다.

## 5. 표준 질문 템플릿 — 상황 유형별 (2N-6 Phase 1 — Q4)

아래 템플릿의 `<>`를 항목 내용으로 채워 쓴다. 요청자료 필드는 `kssb_requirement_catalog.md`
**항목별 상세 기준의 요청자료 기본값**을 시작점으로 하고, 자료에서 확인된 맥락(조직명·제도명 등)으로 구체화한다.

| 상황 유형 | 질문 템플릿 | 질문사유 템플릿 |
|---|---|---|
| 확인 불가(근거 없음) | "<공시요구 내용>을 확인할 수 있는 자료가 있습니까?" | "(제공/공개)자료에서 <필수 요소>에 대한 직접 근거가 확인되지 않음" |
| 일부 근거 — 정량 수치 부족 | "<항목>의 정량 수치(값·단위·대상 기간)와 산정 기준을 확인할 수 있는 자료가 있습니까?" | "<확인된 정성 근거>는 확인되었으나 정량 수치·단위·기간이 확인되지 않음" |
| 일부 근거 — 구체성 부족 | "<확인된 서술>의 구체 내용(<부족한 필수 요소>)을 확인할 수 있는 내부 문서가 있습니까?" | "확인된 근거만으로는 <부족한 필수 요소>의 충분성을 확인할 수 없음" |
| 상충 또는 해석 필요 | "<서술 A>와 <서술 B>가 서로 다르게 읽힙니다. 산정 기준·범위·기준연도의 차이를 확인할 수 있는 자료가 있습니까?" | "자료 내 서술이 상충하여 기준·범위 확인이 필요함(자동으로 해소하지 않음)" |
| 판독 불가(스캔·이미지·미지원) | "<위치 단서> 구간은 자동 판독되지 않았습니다. 해당 부분의 기계판독 가능한 원문(텍스트·데이터표)을 제공해 주실 수 있습니까?" | "문서가 자동 판독되지 않아(스캔/미지원 등) 근거를 확인할 수 없음" |
| 조건부 항목 적용 확인 | "<조건부 제도(예: 내부 탄소가격)>를 운영하고 계십니까? 운영하신다면 관련 기준 문서가 있습니까?" | "적용 조건이 자료에서 확인되지 않음(미적용으로 단정하지 않음)" |

- 질문사유는 실제 상황과 일치해야 한다(`evidence_mapping_rules.md` §7 사유-상황 일치 —
  partial과 not_verifiable의 사유를 교차 사용하지 않는다).
- 판정 확정 표현("미공시", "미준수")을 질문·사유에 넣지 않는다(§4 재확인).

## 6. 표준 요청자료 분류 (공통)

**항목별 기본값의 단일 기준은 `kssb_requirement_catalog.md` 항목별 상세 기준이다.** 아래는 요청자료를
구성할 때 조합하는 공통 분류다.

- **규정·체계 문서**: 이사회·위원회 규정, 리스크 관리 규정, 내부 보고 체계 문서, 위임전결 규정.
- **활동 기록**: 이사회/위원회 안건 목록·의사록(지속가능성 안건), 경영진 보고 자료.
- **산정·데이터 자료**: 산정 명세(경계·방법론), 데이터표(사업장·에너지원별·카테고리별), 기준연도·목표 관리 자료.
- **판독 대체 자료**: 기계판독 가능한 원문(텍스트 PDF·데이터 파일), 자동 판독되지 않은 구간의 원본 데이터.

요청자료는 **고객이 이미 보유했을 법한 문서를 우선** 요청하고, 신규 작성이 필요한 자료는
후속조치(컨설팅 단계의 작업)로 구분한다.

## 7. 예시(공개자료 검증 모드)

- 항목ID: `metric-01`
- 항목명: 온실가스 Scope 1·2 배출량(정량 지표)
- 질문: Scope 1·2 온실가스 배출량의 정량 수치와 산정 기준(경계·방법론)을 확인할 수 있는 자료가 있습니까?
- 질문사유: 공개자료에서 정량 수치·산정 기준 근거가 확인되지 않음
- 관련근거: 해당 없음
- 우선순위: 상
- 요청자료: 온실가스 인벤토리 산정 명세, 배출량 데이터표, 산정 경계·방법론 문서
- 후속조치: 자료 수령 후 산정범위·기준연도 원문 대조
