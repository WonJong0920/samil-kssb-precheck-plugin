# Samil KSSB Precheck

> **KSSB 공시 컨설팅 착수 단계의 근거 검토와 고객 확인 질문 작성을 지원하는 Codex 플러그인**

## 1. 프로젝트 한눈에 보기

Samil KSSB Precheck는 지속가능성 공시 컨설턴트의 **착수 단계 검토 업무**를 지원하는 Codex 플러그인입니다.

- **목적**: 고객 보고서를 KSSB 공시 요구사항과 대조해 **컨설턴트 검수용 DOCX 사전검토 보고서 초안**을 생성
- **대상**: 삼일회계법인 등 ESG·지속가능성 공시 컨설팅 조직의 컨설턴트
- **배경**: 착수 단계의 반복적 근거 대조 업무 부담과, 일반 생성형 AI의 근거 추적 단절·확인 불가 항목의
  임의 확정·결과 비재현 한계
- **수행 방식**: 요구사항별 근거를 **원문 인용·페이지와 연결**하고, 확인할 수 없는 항목은 추정 없이
  **고객 확인 질문·요청자료로 전환**
- **특징**: 근거 없는 긍정 판정 불가(데이터 계약으로 강제) · 검증 오류 시 **보고서를 생성하지 않고 중단**
- **검증**: 실제 126페이지 공개 보고서 end-to-end 실행, 인용 전수 원문 대조(17/18건 재확인·페이지 불일치 0건),
  문서 유형별 샘플 8종 실행 검증
- **책임 범위**: 감사·인증·준수 판단을 대체하지 않으며, **최종 판단은 컨설턴트**가 수행

> **고지**: 본 플러그인은 AX 해커톤 제출을 위해 삼일회계법인의 공개 ESG·지속가능성 공시 자문 맥락을 바탕으로
> 설계했습니다. 삼일회계법인의 공식 제품 또는 내부 도구가 아니며, 감사·인증·준수 판단을 대체하지 않는
> 컨설턴트 검수용 보조 도구입니다. 실제 업무에서는 고객 제공자료를 사용하며, 본 데모와 검증에서는
> 공개 지속가능경영보고서를 대체 입력으로 사용했습니다.

## 2. 해결하려는 문제와 시장 근거

KSSB 공시 컨설팅의 착수 단계에서 컨설턴트는 장문의 지속가능경영보고서·사업보고서·증빙을 기준서
요구사항별로 반복 대조해 "근거가 확인되는 항목 / 부족한 항목 / 확인 불가 항목"을 가르고, 부족한 항목마다
고객 확인 질문과 요청자료를 정리해야 합니다. 이 작업은 시간이 많이 들고 담당자별로 결과 형식이 달라지며,
일반 생성형 AI에 맡기면 근거 추적이 끊기고 확인 불가 항목을 그럴듯하게 확정해 버리며 같은 입력에도
결과가 달라져 검수가 어렵습니다.

**공개 근거 출처 (문제의 실재 — 공개 자료로 확인 가능)**

- **KSSB 지속가능성 공시기준 첫 번째 세트 확정**: 한국회계기준원 지속가능성기준위원회(KSSB), 제1호
  '일반사항'(IFRS S1 기반)·제2호 '기후 관련 공시'(IFRS S2 기반) **2026년 2월 26일 최종 의결**(공개 발표).
- **지속가능성 공시 제도 로드맵 초안**: 금융위원회, **2026년 2월 25일 발표**(공개 의견수렴 ~2026.3.31) —
  2028년(FY2027)부터 대형 상장사 단계적 공시 의무화 방향 제시.
- **삼일회계법인 공개 간행물**: "지속가능성 공시 제도 로드맵 초안 및 확정 공시기준 주요 내용"
  (Sustainability Platform, 2026.03, S/N 2603W-RP-035, samil.com 공개 자료) — 기업 준비 5대 과제로
  공시 거버넌스·데이터 관리체계·재무영향 분석 등 **초기 검토·준비 수요**를 명시.
- **검증 입력 자료**: 공개 발간 지속가능경영보고서(2024년판, 126페이지 PDF) — 아래 검증 결과의 실측 대상.

즉 "KSSB 의무공시 대비 초기 검토"는 확정 기준·정부 로드맵·대상 기업(삼일)의 공개 간행물로 실재가 입증되는
현재진행형 실무 문제입니다.

## 3. 제안 솔루션

**기존 업무 흐름**

```
보고서 수령 → 기준서 체크리스트 확인 → 관련 페이지 수작업 검색 → 근거 발췌
→ 부족정보 판단 → 고객 확인 질문 작성 → Word 보고서 작성
```

**플러그인 적용 후**

```
보고서 입력
→ KSSB 요구사항별 근거 매칭 (판정 라벨 5종: 근거 확인 / 일부 근거·보완 필요 / 확인 불가 / 상충·해석 필요 / 범위 외)
→ 부족정보·고객 확인 질문·요청자료 초안 자동 구조화
→ 자동 품질검증 (오류 시 보고서를 생성하지 않고 중단)
→ DOCX 사전검토 보고서 생성
→ 컨설턴트 검수·수정·확정
```

컨설턴트의 역할이 "찾고 옮겨 적는 작업"에서 **"검수하고 판단하는 작업"**으로 이동합니다.

### 직접 실행 (데모)

**실사용 경로 (Codex, 약 5분)**: ① 이 저장소를 로컬 marketplace로 추가하고 플러그인
`samil-kssb-precheck`를 설치합니다(`.agents/plugins/marketplace.json`) → ② 공개 지속가능경영보고서
PDF(텍스트 판독 가능본)를 첨부하고 **"이 보고서 검토해줘"**라고 요청합니다 → ③ 산출된
`<보고서명>_KSSB_공시근거_사전검토보고서.docx`를 확인합니다.

**내부 구성요소만 빠르게 (로컬, 약 2분)** — 번들 예시 findings로 검증·변환의 결정 동작을 확인합니다:

```
node src/validators/kssb_findings_validator.cjs src/schemas/kssb_findings_example.json   # 오류 0
node src/renderers/kssb_report_delivery.cjs src/schemas/kssb_findings_example.json -o <임시폴더>
# → DOCX·HTML·Markdown 생성, 재실행 시 byte-identical. 오류 findings에서는 보고서 미생성·중단(exit 4)
```

## 4. 기존 방식과의 차별성

| 구분 | 수작업 체크리스트 | 일반 챗봇 | 일반 RAG 검색 | 본 플러그인 |
|---|---|---|---|---|
| KSSB 업무 절차 내장 | 부분 | 없음 | 없음 | **있음** (요구사항 카탈로그·판정 라벨·질문 규칙) |
| 원문 근거 연결 | 수동 | 불안정 | 가능 | **필수** (근거 없는 긍정 판정 불가) |
| 확인 불가 처리 | 담당자 의존 | 추정 위험 | 검색 실패로 종료 | **질문·요청자료로 전환** |
| 결과 형식 일관성 | 낮음 | 낮음 | 중간 | **높음** (고정 스키마) |
| 오류 시 생성 중단 | 없음 | 없음 | 보통 없음 | **있음** |
| 최종 전문가 검수 | 필수 | 불명확 | 불명확 | **명시적 전제** |

핵심 차별점 다섯 가지입니다.

1. **근거 없는 긍정 판정 방지** — "근거 확인" 판정은 원문 인용과 위치 단서에 연결되어야만 성립합니다.
2. **모르는 내용의 질문 전환** — 자료에서 확인할 수 없는 내용은 추정하지 않고 고객 확인 질문·요청자료로 변환합니다.
3. **업무 절차의 표준화** — 자유형 요약이 아니라 KSSB 요구사항 카탈로그, 판정 라벨, 질문 규칙, 출력 스키마를 따릅니다.
4. **오류 결과의 전달 차단** — 자동 검증에서 오류가 발견되면 보고서를 생성하지 않습니다.
5. **전문가 판단 유지** — 감사·인증·준수 판단을 수행하지 않으며, 최종 판단은 컨설턴트가 담당합니다.

## 5. 검증 결과 (실측 기록)

실제 공개 지속가능경영보고서(126페이지 PDF)를 입력으로 **KSSB 4대 영역 요구사항 카탈로그 10개 항목 전부**를
end-to-end 실행하고, 산출 보고서의 인용을 입력 원문과 전수 대조해 기록으로 남겼습니다.

- **실보고서 완주**: findings 생성 → 자동 검증(오류 0) → DOCX 사전검토 보고서까지 완주
  ([실행 evidence](docs/samples/b3_node_runtime_and_real_ux_evidence_2026-07-09.md)).
- **인용 전수 대조** ([대조 기록](docs/planning/usertest_output_quality_review_2026-07-09.md)):
  - 원문 재확인 성공: **17/18건** (공백 정규화 외 원문 그대로 재발견)
  - 페이지 위치 불일치: **0건** (18건 모두 주장한 페이지와 일치)
  - 인용 단위 개선 필요: **1건** — 표의 비연속 셀을 하나의 인용으로 결합한 사례. 페이지 오류는 아니었으나
    인용 단위가 부적절하다고 판단해 인용 선택 지침을 보완했습니다.
- **원문 불일치 인용의 사전 수정**: source-bound 재검 절차에서 추출 결과와 원문이 일치하지 않는 인용 후보
  **3건을 발견해 보고서 생성 전에 수정**했습니다.
- **재현성**: 동일 findings에서 보고서 재생성 시 **byte-identical** (반복 실측 + 자동 테스트).
- **안전 중단**: 검증 오류가 있으면 보고서를 만들지 않고 문서화된 종료 코드로 중단합니다 —
  오류 상태의 그럴듯한 보고서가 전달되지 않습니다.
- **자동 테스트**: Node 내장 테스트 **365건 통과**, 외부 패키지 의존성 **0**.
- **검증 범위(문서 유형별 샘플 8종)**: 위 대표 실측 외에, 대형 PDF(359페이지 경영실적보고서)·텍스트+혼합
  PDF(금융그룹 KSSB 보고서)·스캔 전용 PDF·HWP·HWPX·DOCX·텍스트 PDF 등 **8종 샘플로 보고서 생성과
  보조 판독 경로(구조 판독·OCR 대상 식별)를 실행 검증**했습니다. 초기 산출물 검수에서 발견된 인용 품질·
  검토 범위 표기 문제는 검토 규칙으로 반영해 개선했습니다 — **실행 → 검수 → 규칙 개선의 반복**으로
  품질을 끌어올린 과정 전체가 저장소와 로그에 기록되어 있습니다.

> 위 수치는 전부 저장소 문서에 기록된 실측이며, 제품 완성이나 감사·인증 수준의 보증을 의미하지 않습니다
> (컨설턴트 검수 전제). 인용 전수 원문 대조는 대표 실측(126페이지 보고서) 기준입니다.

**심사자 직접 확인 포인트**: 위 데모(§3 직접 실행)로 생성한 보고서에서 ① 아무 인용이나 골라 원문 PDF
검색(Ctrl-F)으로 주장한 페이지에서 재발견되는지, ② 근거 없는 항목이 "미공시" 단정 없이 고객 확인 질문·
요청자료로 전환되는지, ③ 고지·검수 경계 문구가 포함되는지 확인할 수 있습니다.

## 6. AI 활용과 판단 책임

이 플러그인은 "AI가 다 한다"가 아니라 **판단 주체를 명확히 분리**하는 설계입니다.

| 주체 | 수행하는 일 |
|---|---|
| **LLM (Skill)** | 문서에서 관련 근거 후보 탐색 · 요구사항별 판정 초안 · 부족정보와 고객 질문 생성 |
| **코드 (검증기·렌더러)** | 필수 필드·근거 참조·허용 라벨·금지 표현 검사 · 오류 시 보고서 생성 차단 · 결정적 문서 변환 |
| **사람 (컨설턴트)** | 근거의 적합성 판단 · 최종 공시 판단 · 고객 커뮤니케이션 확정 |

인용의 원문 실재성 자체는 코드가 아니라 생성 절차 내 재검 규율과 사람 검수가 담당하며,
위 검증 결과의 인용 대조가 그 실효성 기록입니다.

**개발 과정의 AI 활용**: 구현 AI(Claude Code)와 독립 리뷰 AI(Codex)를 분리해 모든 실질 변경이
독립 리뷰를 거치는 방식으로 개발했습니다. 그 전체 대화 기록이 `logs/` 폴더에 **무편집 원본**으로
수록되어 있어, 제출 로그·플러그인·답변 간 개발 과정을 그대로 추적할 수 있습니다.

## 7. 삼일회계법인 업무 적합성

이 플러그인은 삼일의 전문 판단을 자동화하는 제품이 아니라, **전문 판단 전에 수행되는
문서 대조·근거 정리·질문 초안 작성을 표준화하는 도구**입니다.

회계법인 환경의 요구와 다음과 같이 정합합니다.

- **근거 보존**: 모든 판정이 원문 인용·위치와 연결되어 검토 근거가 남습니다.
- **과잉 확정 금지**: "근거 확인"은 근거의 존재를 뜻할 뿐 준수 확정이 아니며, 금지 표현(준수 확정·적합
  판정·인증 의견 등)은 스키마와 검증기가 차단합니다.
- **검수 전제**: 산출물은 초안이며 컨설턴트 검수·확정을 전제로 합니다.
- **재현성**: 동일 findings에서 동일 문서가 재생성되어 품질관리·재검토에 유리합니다.

**도입 시나리오**: 컨설턴트가 신규 고객사의 지속가능경영보고서를 입력합니다. 플러그인은 KSSB
요구사항별로 관련 원문과 페이지를 정리하고, 근거가 부족한 항목은 고객 확인 질문과 요청자료로 전환합니다.
컨설턴트는 생성된 DOCX를 검토해 고객 인터뷰 질문지와 초기 gap 검토 자료로 활용합니다.

## 8. 지원 범위·한계·위험 대응

**현재 제공**

- KSSB 4대 영역(거버넌스·전략·위험관리·지표 및 목표) 요구사항 카탈로그 **10개 항목** 기반 검토
  (전체 KSSB 기준서를 커버하는 것은 아니며, 카탈로그는 분리 관리되어 확장 가능합니다)
- source-bound 근거 연결·판정 라벨 5종·부족정보·고객 확인 질문·요청자료·보완 권고 생성
- 자동 검증(오류 시 생성 중단)과 DOCX·HTML·Markdown 보고서 생성
- 텍스트 기반 PDF 기본 지원. 스캔·혼합 PDF와 HWP 계열 문서는 **사용자 승인 기반 보조 판독 경로** 제공
  (상세: [사용자 Quickstart](docs/user_quickstart_pre_2n_5.md))

**현재 미지원**

- 이미지·차트의 의미 해석, 무승인 자동 OCR
- 감사·인증·준수 확정 판단
- 다수 고객 프로젝트 관리·협업 기능

**위험과 대응**

| 위험 | 대응 |
|---|---|
| LLM이 근거를 과도하게 해석 | 원문 인용 앵커 강제, 확인 불가 라벨·질문 전환 |
| 문서 추출 오류 | 승인 기반 보조 판독 경로, 사람 검수 전제 |
| 기준 변경 | 요구사항 카탈로그를 코드와 분리해 관리 |
| 고객 자료 보안 | 로컬 실행, 외부 패키지 의존성 0 |
| 잘못된 보고서 전달 | 검증 오류 시 보고서 생성 차단 |
| 도구 성격 오해 | 감사·인증·준수 판단 제외를 산출물 고지문에 명시 |

**확장 방향** (전문가를 대체하지 않고, 판단 전 반복 작업의 구조화를 넓히는 방향)

1. **사전검토 자동화 고도화** — 다문서 통합 검토, 산업별 요구사항 카탈로그 확장
2. **프로젝트 협업** — 고객별 검토 이력, 검수 상태, 근거 변경 추적
3. **지식자산화** — 반복 이슈 패턴, 질문 템플릿, 조직 차원의 품질관리 기반

## 9. 기술 구조

사용자 진입점은 **Skill 하나**이며, 내부는 판단과 검증·변환을 분리한 선형 파이프라인입니다.

1. **Skill (판단)** — 입력 자료만을 근거로 요구사항별 판정·원문 인용·부족정보·질문을
   **구조화 findings**(JSON Schema 계약)로 생성 ([SKILL.md](src/skills/samil-kssb-precheck/SKILL.md) ·
   [데이터 계약](src/schemas/findings_schema_contract.md))
2. **검증기 (detect-only)** — findings를 재판정 없이 점검하고 문제를 보고만 합니다. 오류가 있으면
   보고서를 생성하지 않고 중단합니다.
3. **렌더러·전달 (형식 변환)** — 동일 findings를 재판정 없이 **DOCX → HTML → Markdown**으로 결정적으로
   변환하고, 로컬 경로·내부 로그를 노출하지 않는 사용자 요약을 제공합니다.
4. **사람 검수** — 산출물은 초안이며 컨설턴트가 확정합니다.

핵심 파이프라인은 외부 연결을 최소화한 **선형·결정적 구조**로 설계해 재현성과 검증 가능성을
우선했습니다. 실행 런타임은 Node 내장 모듈만 사용하며(외부 패키지 0), Python 구현을 동작 대조용
참조 기준으로 병행 유지합니다. 상세 흐름: [docs/workflow_usage.md](docs/workflow_usage.md)

```
├── src/                                  # 플러그인 루트
│   ├── .codex-plugin/plugin.json         # 플러그인 매니페스트
│   ├── skills/samil-kssb-precheck/       # Skill 본체(진입점)와 검토 기준 문서
│   ├── schemas/                          # findings 데이터 계약(JSON Schema)·예시
│   ├── validators/                       # 자동 품질검증(detect-only)
│   ├── renderers/                        # DOCX·HTML·Markdown 생성·전달
│   └── intake/                           # 선택적 문서 판독 보조(승인 기반)
├── .agents/plugins/marketplace.json      # 로컬 marketplace 정의(설치용)
├── docs/                                 # 데모·검증·핵심 설계 문서
├── logs/                                 # 개발 과정 AI 대화 로그(무편집 원본)
└── README.md
```

## 10. 제품 경계와 제출물 안내

- 감사·인증·준수 판단을 **대체하지 않습니다.** 산출물은 초안이며 컨설턴트 검수를 전제로 합니다.
- 확인 불가 항목을 미공시로 단정하지 않습니다. "근거 확인"은 근거의 존재를 뜻할 뿐 준수 확정·감사의견·인증이 아닙니다.
- 삼일회계법인의 공식 제품·내부 도구가 아닙니다.
