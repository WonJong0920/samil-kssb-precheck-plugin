# 예선 과제 요건 대조 검토 (submission.zip·로그·질문 5문항)

> **성격**: 공개된 예선 과제 본문("참여 기업의 공개·검증 가능한 문제를 해결하는 Codex 플러그인")과
> 현 repo 상태의 대조 검토. B6 review PASS(`docs/reviews/codex_b6_submission_readiness_review.md`) 이후의
> 제출 실행 준비 문서다. 최종 제출 판단·업로드는 사용자 수행.

## 1. 요건 대조표

| 과제 요건 | 현 상태 | 판정 |
|---|---|---|
| zip 루트에 `src/` — **전체 플러그인 루트가 src 안** | `src/` = plugin root(marketplace `source.path=./src`), B5-A~D로 자기완결 검증 | **충족** |
| `src/.codex-plugin/plugin.json` **필수** | 존재·파싱 정상·version 0.2.0 | **충족** |
| plugin.json 외 **동작 구성요소 ≥ 1** | Skill `skills/samil-kssb-precheck/SKILL.md` + 실행 코드(validator/renderer/delivery `.cjs`, 스키마) | **충족** |
| `.mcp.json` (필요 시) | 미채택 — **의도적 설계 결정**(선형·결정적 파이프라인에 MCP 불필요, README "설계 선택과 근거"에 문서화) | 해당 없음(근거 문서화됨) |
| zip 루트 `README.md` | 존재 — 문제 정의·사용자·작동·검증 실적 구조 | **충족**(§3 보강 1건) |
| zip 루트 `logs/` — **AI 대화 로그 원본 무편집 전체**(md/txt/json/jsonl) | **공식 log-hooks 설치·작동 중** — `logs/claude-code/*.jsonl` + `logs/codex/rollout-*.jsonl` 자동 수집 확인(로컬, git 미추적 정상) | **수집 중 — 제출 시 포함**(§4) |
| 기업 1개당 플러그인 1개 별도 제출 | 삼일회계법인 단일 대상 단일 플러그인 | **충족** |
| 문제를 **공개 자료로 입증**(AI가 확인 가능, 비공개·출처없는 숫자 불인정) | 문제·검증의 근거가 전부 공개 자료(KSSB 확정 기준·금융위 로드맵·삼일 공개 간행물·공개 지속가능경영보고서)이나 **README에 출처 명시가 없었음** | **보강 완료**(§3) |
| 질문 5문항 | 답변 초안 §5 (제출 시 사용자 확정) | **초안 준비** |
| ⚠ 실격: 로그 사후 가공(편집·발췌·삭제) | 기존 정책(§2 원본·무편집 원칙, 요약·삭제로 대체 금지)과 **정합** | 준수 태세 |

- **정합성 채점 대응**("로그·플러그인·질문지 정합"): 이 repo는 전 개발 과정이 Claude Code 작업 ↔ Codex 독립 리뷰
  사이클(`docs/reviews/` 50+건)로 기록되어 있고 로그가 그 과정 자체다 — 로그·플러그인·답변이 구조적으로 일치.
- **log-hooks/ 취급 명확화**: packaging policy §1의 "사전 존재 세션 로깅 인프라"는 **해커톤 공식 로그 수집 도구**로
  확인됨. 도구 자체는 제출물이 아니므로 zip 미포함 유지(**수집된 `logs/`만 제출**) — 기존 E-분류와 모순 없음.

## 2. submission.zip 조립 절차 (제출 단계 실행용)

1. packaging policy §4 최종 preflight 실행(§4.3 Node 게이트는 B5-D·B6에서 green 실증 — 제출 직전 재실행).
2. 스테이징 폴더에 **git tracked 파일만** 전개: `git archive HEAD` → 원본 PDF(`usertest/`)·생성 산출물·
   `log-hooks/`·`node_modules` 등은 **미추적/ignore라 자동 제외**된다.
3. 로컬 `logs/`(claude-code·codex jsonl **원본 그대로**)를 스테이징의 `logs/`에 복사 —
   **어떤 편집·발췌·삭제도 하지 않는다**(실격 조건). 제출 직전 마지막 세션 로그까지 포함.
4. 비밀값 확인(가공 아님 — 존재 확인만): API 키·토큰·비밀번호 패턴 스캔. 과제 경고대로 애초에 입력한 적 없어야
   하며, 로컬 경로·계정명은 비밀정보가 아니므로 발견되어도 **원본 유지**(무편집 원칙 우선).
5. zip 생성(zip 루트 = `src/`·`README.md`·`logs/`·`docs/`·`tests/`·`.agents/` 등 tracked 전체 + logs).
   과제 트리는 최소 요건이며 "src 안 구조 자유" — `docs/`(evidence·리뷰)·`tests/` 포함은 README 링크
   무결성·정합성 채점에 유리하다고 판단. zip은 repo에 커밋하지 않는다.
6. 질문 5문항 답변(§5 초안)을 제출 양식에 맞춰 사용자 확정·입력.

## 5. 질문 5문항 답변 초안 (사용자 확정용)

1. **무엇을, 누가, 어떤 상황에서 쓰나요?**
   삼일회계법인 등 ESG·지속가능성 공시 컨설팅 조직의 컨설턴트가, 고객사 KSSB 공시 컨설팅 착수 시
   고객 제공 보고서·증빙을 KSSB 4대 영역(거버넌스·전략·위험관리·지표및목표) 공시요구와 대조해
   "확인 근거 / 부족 정보 / 고객 확인 질문·요청자료"를 정리하는 **초기 사전검토 워크페이퍼 초안**을
   생성할 때 사용한다(해커톤 검증은 공개자료 대체 입력).
2. **왜 이 문제를 선택했나요?**
   KSSB 지속가능성 공시기준 첫 세트가 2026.2.26 확정되고 금융위 공시 로드맵 초안(2026.2.25)이 발표되어
   FY2027 의무공시 대비 수요가 공개적으로 확인되는 시점이다(README "공개 근거 출처"). 그 초기 검토는
   반복·소모적 대조 작업인데, 일반 챗봇 방식은 근거 추적 단절·환각 인용·확인 불가의 과잉 확정·비재현성
   때문에 감사법인 환경에서 쓸 수 없다 — 규율 있는 도구가 필요한 실무 문제다.
3. **플러그인은 어떻게 작동하나요?**
   진입점은 Skill 하나. ① Skill이 입력 자료만을 근거로(source-bound) 항목별 판정·원문 인용·부족정보·
   고객질문을 구조화 findings(JSON 계약)로 생성 → ② detect-only 검증기가 재판정 없이 preflight(오류 시
   보고서를 만들지 않고 통제된 중단) → ③ 렌더러가 재판정 없이 DOCX→HTML→Markdown으로 결정적 변환 →
   ④ 컨설턴트 검수(산출물은 초안, 감사·인증·준수 판단 대체 아님). 런타임은 Node 내장 모듈만(의존성 0).
4. **AI를 어떻게 활용했나요?**
   제품 안: LLM은 **판단(findings 생성)만** 담당하고, 검증·변환은 결정적 코드로 분리해 근거 없는 확정을
   스키마 수준에서 차단했다. 개발 과정: Claude Code(구현)·Codex(독립 리뷰·PASS/FAIL 게이트)·ChatGPT(작업
   분기)의 3-에이전트 역할 분리로 모든 실질 변경이 독립 리뷰를 거쳤다(`docs/reviews/` 기록, 제출 로그가
   그 과정 원본이다).
5. **어떻게 검증했나요?**
   자동: Node 테스트 365건·Node↔Python parity·byte-identical 결정성·오류 시 hard stop. 실측: 실제 공개
   126페이지 지속가능경영보고서로 end-to-end 완주 후, 산출 보고서의 인용 18건을 입력 원문과 전수 대조 —
   17건 원문 재발견(페이지 정확도 100%), 예외 1건은 표 비연속 인용으로 식별해 지침 보강. 실행 중
   source-bound 재검 규율이 불일치 인용 3건을 실제 차단했다. 상세: README "검증 실적" + repo evidence 문서.
